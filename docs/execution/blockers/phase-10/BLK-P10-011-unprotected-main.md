# BLK-P10-011: `main` does not enforce the Release B required checks

- Severity: P1 release-control defect
- Status: repaired locally; remote configuration pending the authorized Release B action
- Affected action: TASK-P10-011 Release B pull-request merge only
- Production impact: none; no branch setting, push, pull request, merge, deployment, or production write was changed

## Reproduction and impact surface

An authenticated read-only GitHub query on 2026-08-04 returned repository admin/push permission but `GET /repos/Elfsa-Miranda/GO_NOW/branches/main/protection` returned HTTP 404 `Branch not protected`. The approved contract requires `main` to move only through the Release PR under platform required checks and forbids bypassing protected-branch policy. The existing live verifier queried the pull request, check runs, and Git commit trees, but could accept an unprotected branch when those three check runs happened to be green. The defect affects P10-011 and the structurally equivalent final Release C publication; it does not invalidate local Phase 10 or Phase 11 code/test evidence.

## Reversible repair

One shared evaluator now performs an authenticated, read-only branch-protection query for both P10-011 and REL-C-001 in addition to their existing live PR queries. Both fail closed unless `main` has the exact required check set (`agent-required`, `baseline-and-candidate`, `tracked-and-history`), strict head synchronization, administrator enforcement, pull-request-only changes, force pushes disabled, deletions disabled, and linear history disabled so the required two-parent merge remains possible. Missing `GH_TOKEN`/`GITHUB_TOKEN`, HTTP 404, an extra or missing required check, or any bypass setting is a release-gate failure. Both task requests record this configuration as a prerequisite and explicitly state that the current PR adapter is not authorized to manage branch protection.

`docs/execution/commands/Invoke-GitHubMainProtection.ps1` is the local settings enabler. Its default `Verify`/`Plan` paths are read-only. `Apply` requires a process-scoped token, explicit authorization and actor references, and an expected current-state SHA-256; it refuses to overwrite any existing non-compliant rule and only creates the exact rule from an absent state. The rule requires the three checks, strict synchronization, administrator enforcement and pull-request-only changes, with zero automated-profile reviewer count, no bypass actors, no force pushes/deletions, and linear history disabled for the required two-parent merge. It writes only hashes of authorization/actor references and never records the token. A second authenticated GET must equal the desired canonical state or the action fails closed.

The isolated adapter contract suite covers read-only planning, exact request construction, current-state CAS rejection, refusal to overwrite an existing rule, postcondition rejection, receipt redaction, rollback planning, and exact managed-state rollback. It is called by the repository TaskGate contract suite and by the `agent-required` workflow; changes to either the adapter or its test also trigger that workflow. A live authenticated read-only Plan on 2026-08-04 confirmed `current_state=absent`, current canonical state SHA-256 `00c26121ab43694c9459277fcee58e372987ed2b6ccf692bd6bc6eefdb8355af`, desired canonical state SHA-256 `9d00cd307ce7775684c586270a8ccb0e01d6c7a2adb182f2de383364e407c431`, and `mutation_performed=false`.

The same adapter makes rollback reversible without broadening it: deletion requires the completed apply receipt, a new explicit rollback authorization, and a CAS proof that the live rule is still byte-semantically equal to the adapter-managed state whose predecessor was absent. It then verifies HTTP 404 and records a separate rollback receipt. Existing protection, concurrent drift, missing token, missing authorization, or an unexpected API response blocks only that settings action. The adapter is implemented and fake-isolated tests are safe to run locally; no remote setting is changed until the explicit settings authorization exists. Until then, only P10-011/Release PR merge is blocked; local certification, repair, Phase 11 materialization, and evidence work continue. Rollback of the verifier code is a non-force revert, but reverting would restore the unsafe false-positive path and therefore cannot authorize a release.
