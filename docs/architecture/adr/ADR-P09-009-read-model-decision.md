# ADR-P09-009: Keep normalized reads; do not add a read model

- Status: local provisional `not_applicable`; formal Data and SRE review pending
- Date: 2026-08-02
- Owners: Architecture, Data, SRE
- Scope: Phase 9 itinerary Agent read paths only

## Context

Phase 9 adds typed Candidate preview and a guarded Domain Command adoption transaction. A separate CQRS read model would add another data owner, projection logic, replay/rebuild behavior, freshness objectives, storage, and operational failure modes. The governing contract forbids adding that boundary without concrete multi-join, latency, sample, and lag evidence.

The repository has no approved production workload export or production SLA for these reads. To avoid converting that unknown into a claim, `test_read_model_need.py` pre-registers a local synthetic decision fixture. It measures three current query shapes against explicit local initial hypotheses:

| Query ID | Shape | Local p95 initial hypothesis | Samples |
|---|---|---:|---:|
| `run_status_by_tenant` | tenant/run key lookup, 0 joins | 50 ms | 40 + 5 warmups |
| `adoption_receipt_with_delivery` | receipt → approval → outbox, 2 joins | 50 ms | 40 + 5 warmups |
| `itinerary_detail_with_activities` | itinerary → ordered activities, 1 join | 50 ms | 40 + 5 warmups |

The fixture also performs 40 commit-to-read visibility samples with a 50 ms local p95 initial hypothesis and requires zero stale reads. It contains only deterministic synthetic identifiers. Its measurements are suitable for deciding whether Phase 9 should add code now; they are not a production SLA, capacity result, or authorization to deploy.

## Decision

The decision is `not_applicable`: keep PostgreSQL normalized tables as the fact source and add no CQRS read model in Phase 9. The mechanically generated report must show all three direct query profiles meeting their local p95 hypothesis, 120/120 measured query samples, 40/40 source-visibility samples, zero stale reads, and zero production writes.

Ownership remains explicit:

- Domain and Data own normalized business/runtime facts.
- Architecture owns this boundary decision.
- No read-model owner is assigned because no projection exists.
- Data and SRE must approve a future ADR before any projection, backfill, retention, or freshness boundary is introduced.

Re-evaluation requires an approved workload with at least 100 samples per query in each of three consecutive windows, at least two user-critical direct queries missing their approved p95 SLA, and a proposed projection able to maintain p95 lag at or below 5 seconds. The future decision must include source load, correctness/rebuild behavior, tenant isolation, retention/deletion propagation, cost, and rollback evidence.

## Alternatives considered

| Option | Safety and data | Compatibility | Cost and rollback | Decision |
|---|---|---|---|---|
| Add a read model now | Introduces an unmeasured stale-data and deletion-propagation boundary | New API/version semantics would be required | Highest build and operations cost; backfill rollback required | Rejected |
| Add an application cache | Adds invalidation and per-instance consistency without proving a bottleneck | May change freshness unpredictably | Moderate cost; cache flush is reversible but hides the root need | Rejected |
| Keep normalized reads and measure | One database remains the fact source; no new tenant/data copy | Preserves current API and old/new client paths | Lowest cost; no migration or rollback | Selected |

## Evidence and limitations

The canonical local evidence is `docs/execution/evidence/phase-09/P09-009/read-model-report.json`, generated by the five-case performance contract and bound to its JUnit and artifact hashes. It records every query ID, join count, threshold, sample count, observed p95/max, visibility result, decision, reason code, ownership, trigger, and `production_claim_authorized=false`.

SQLite is intentionally used only as a deterministic, dependency-free decision fixture; it is not a PostgreSQL performance proxy. Therefore this ADR does not assert production latency, production throughput, user benefit, or deployed schema facts. A production decision requires an authorized PostgreSQL-like environment and approved workload evidence.

## Consequences and rollback

No production table, migration, service, queue, cache, API, or feature flag is added. Existing Candidate preview, Domain Command, Event, and outbox paths remain unchanged. The decision is reversible by a later approved ADR when the trigger is met. Current rollback is “do not implement”: remove this test/ADR/evidence candidate without changing runtime data or application behavior.
